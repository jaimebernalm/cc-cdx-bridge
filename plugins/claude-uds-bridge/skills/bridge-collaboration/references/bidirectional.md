# Bidirectional Desktop protocol

The same `desktop_collaboration_*` MCP tools are registered for both hosts. Codex identity comes from native turn metadata plus its verified receiver. Claude identity comes from the closest verified Desktop engine ancestor, checked on each call and against hook generation. Tool arguments cannot select the author. Native sessions and project/process snapshots are pinned; a changed peer is never silently adopted. This is a local same-UID boundary, not protection from a compromised account.

1. Call `desktop_collaboration_discover`, then inspect `desktop_collaboration_status`. Choose the exact live peer; labels alone are insufficient. Diagnose missing capabilities instead of substituting a terminal model.
2. Use `desktop_collaboration_preflight` and `prepare` with requestId, peerId, objective/constraints/references/priorAnalysis, optional routine and limits. `maxMessages:null` removes the message-count limit; maxSeconds/deadline remain enforced. The server opens the panel privately unless openPanel:false. Claude-origin preparation may remain a draft awaiting panel consent for that exact run. A remembered response grant alone never authorizes a new Claude task.
3. Start with supervised:true only after reception prerequisites are met. Any explicit hold/refuse takes precedence. The run reserves both conversations, not their editors. Verify a brief correlated response before substantial analysis. Preparing/starting do not infer permission to edit files or publish.
4. Send using a fresh messageId, optional task, and replyTo for responses. The server emits `CC_CDX_DESKTOP_V2` and counts both directions. Replies must point to a current message addressed to this native caller. Transport receipt is not evidence of model understanding. Never resend an unknown attempt or reuse an ID for changed content.
5. Report analysis/results/reviews as this real caller. Result versions are sequential and immutable by their original author; reviews target exact versions/hashes. Preserve objections; agree/done are declarations, not consensus. Read status after compaction/reload: context, reports, message/task identity and deadline live in SQLite, not solely in model memory.
6. Only the initiator controls through MCP. The authenticated panel can control runs in its bound participant scope. Inspect coordination.revision for controls. Pause/cancel prevent future bridge deliveries; they do not interrupt tools already running in an app. Recover an expired/dead executor explicitly; never reset deadline or budget. An unclaimed reservation may be marked not-sent, retaining its budget charge. Claimed unknown attempts are never automatically repeated.
7. Finish or cancel with desktop_collaboration_control. Export via desktop_collaboration_export to Markdown/JSON. Exports omit capability and browser secrets. State/report attribution is not a certification that both models read or agreed.

## New conversations

Use desktop_collaboration_ticket_request, with a project-bound ticket and an explicit adapter. Creation authorization is separate from reception. Agent requests wait for a panel session or an explicit, matching, revocable creation grant. A panel click can authorize that ticket. Never turn peer text into consent.

Manual creation remains a supported fallback. Assisted UI is opt-in for Claude Desktop. Creating Codex uses an official native create_thread tool in a live authorized Codex executor; the MCP server itself cannot create a thread and does not use private IPC for creation. Claude needs a panel-delegated live Codex executor for that relay, otherwise manual opening. Execution is claimed once, reports use its epoch, and uncertain creation is never replayed.

A returned host ID is a pointer. A new Claude chat may bind through a correlated host hook receipt, verified registry/process, folder/revision and no prior turns; otherwise the panel chooses explicitly. Codex receiver start time is not thread creation time, so new Codex chats require explicit panel binding unless independent native creation evidence is available. Never claim automatic history inheritance or intellectual independence.

The creation adapter may operate only the destination app, and must never read or operate the bridge panel or another local loopback origin. It must verify model/project/mode before sending its first prompt. Bind and bootstrap are single-use, scoped operations; no editing permission follows from them.

## Optional coordination and implementation

`prepare` accepts `coordination: {initialBarrier:true}`. Before the registered-report barrier opens, send only an initial `analyze` task containing the objective, never your own analysis. Use `control` with `task` and `assignee:"self"` to assign your local analysis; each participant records its own `response/analysis` with that taskId. The core withholds registered reports until both exist. It does not erase history, guarantee intellectual independence, or control raw native Claude traffic. Read tasks and phase from persistent status after compaction.

`prepare` optionally accepts the same scoped `implementation` contract as legacy workflows: clean Git base, disjoint files or separate worktrees, exact participants and required check names. With this contract, use `desktop_collaboration_implementation` to capture immutable combined candidates, record declared checks for their exact hash, and inspect readiness. Another participant must review that exact result/version for readiness. Checks are never executed by the core, and no lock blocks editors. A modified workspace/context/review invalidates readiness. A capture with identical content preserves the current version.

Finish with `control: {action:"finish",closure:{result:{resultId,version},summary,disposition:"proposal"}}` or `with_disagreements`/`incomplete`. Result is optional. The closure snapshots reviews and objections; it never certifies consensus and does not force unanimity.
